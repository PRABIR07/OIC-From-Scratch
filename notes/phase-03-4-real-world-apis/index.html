1Reading API docs like a pro

Reading a recipe before cookingA good cook reads the whole recipe first: ingredients, oven temperature, timings, “what can go wrong”. Before building any integration, read the API docs with a checklist, and you’ll avoid most surprises.
  1. 1
    Base URL & environmentsTest and production addresses are usually different.
  2. 2
    AuthenticationBasic, API key or OAuth? Which grant, token URL, scopes? (3.3)
  3. 3
    The endpoints you needMethod, path, required parameters, sample request and response.
  4. 4
    PaginationDefault and maximum page size, and how to ask for the next page.
  5. 5
    LimitsCalls per minute/hour/day, and what happens when you cross them.
  6. 6
    ErrorsThe error body’s shape and the codes the API really uses.
  7. 7
    Versioning & changesWhich version you’re on, and where changes are announced.
  8. 8
    Sync or asyncDoes a call finish now, or return a job ID to check later (ch. 11)?

Then prove it in Postman before touching OIC: one successful call with real credentials removes half the risk of any integration.

2Pagination, properly

Photocopying a thick fileThe copier takes 25 sheets at a time. You feed a batch, note where you stopped, feed the next, and stop when the file is empty. Paging is a loop: ask for a batch, remember your place, repeat until the API says there’s no more.
StyleAsk for next page withKnow you’re done whenSeen in
Offsetoffset += limithasMore: false or fewer items than limitOracle Fusion
Page numberpage += 1An empty page, or page > totalPagesMany APIs
CursorThe next token from the last answerNo next tokenLarge modern APIs
Link headerThe URL in Link: <…>; rel="next"No rel="next"GitHub, JSONPlaceholder
Three real-world traps. ① The API has a maximum page size: asking for 10,000 quietly gives you 500. ② Records added or deleted while you page can shift offsets, so you skip or repeat a record. Sort by a stable field (like ID or last-updated date) to reduce this. ③ Never assume one page is everything: always check the “more” signal.

3Filter, sort and choose fields

Ordering at a buffetYou don’t carry the whole buffet to your table and pick there. You take only what you’ll eat. Ask the API for only the records and fields you need. It’s faster, cheaper, and kinder to rate limits.
You wantTypical query parameterWhy it matters
Only some records?dept=HR, ?status=activeFewer pages, fewer calls
Only changed records?updatedSince=2026-10-13T00:00:00ZThe key to daily “delta” syncs
A fixed order?sort=id, ?orderBy=LastUpdateDateStable paging (ch. 2)
Only some fields?fields=id,name,emailMuch smaller responses
Related data in one go?expand=addressesOne call instead of many

The idea of fetching only what changed since the last run is called a delta or incremental sync. Almost every scheduled OIC integration does this: it remembers the last run time and asks only for newer changes.

4Oracle Fusion REST: anatomy

Oracle Fusion’s REST APIs all follow one pattern. Learn it once and you can read any of them.

A collection response, shortened

Each item has a links array with a self link: the exact URL to read or update that one record. Fusion item IDs in URLs can be long encoded keys (00020000…), so use the self link instead of building the URL yourself. Child data (like a worker’s addresses) lives in child resources under the item.

6Writing to Fusion

ActionRequestNote

Date-effective dataAn employee’s salary history is like a diary: Pune until March, Mumbai from April. You don’t erase the old entry; you add a new one from a date. Much of Oracle HCM is date-effective, so updates need to say from when. You’ll go deeper in Phase 8.

For thousands of records, Fusion’s REST APIs aren’t the right tool. You’d use bulk loads instead (FBDI and HCM Data Loader, Phase 8), often through the SOAP service from Part 3.2.

7Rate limits

The bank token machineA busy bank hands out token numbers so the counters aren’t mobbed. If you push in, you’re sent back. A rate limit caps how many calls you may make in a time window. Cross it and you get 429 Too Many Requests.
DoBecause
Filter and choose fieldsFewer, smaller calls (ch. 3)
Use bigger pages (within the max)2,000 records in 4 calls beats 80 calls
Respect Retry-AfterRetrying early just gets another 429
Spread scheduled jobsTen integrations at exactly 00:00 compete for the same allowance

8Retries and backoff

A busy phone lineIf a number is busy, you don’t redial every second; you wait a minute, then a few minutes, then longer. Exponential backoff waits longer after each failure: 1s, 2s, 4s, 8s… and gives up after a few tries. Adding a little randomness (jitter) stops a thousand clients from all retrying at the same instant.
AnswerRetry?Why
Timeout, connection resetYesLikely a blip (but see ch. 9 for POST)
429Yes, after Retry-AfterYou were too fast
502, 503, 504Yes, with backoffUsually temporary
500Maybe onceCould be a real bug; don’t hammer it
400, 401, 403, 404, 409, 422NoThe same request will fail the same way. Fix it.

9Retrying safely: idempotency

Did my payment go through?Your UPI app spins, then times out. Did the money go? If you simply pay again, you might pay twice. A timeout doesn’t mean “failed”: it means “I don’t know”. The request may have succeeded and only the answer got lost.
TechniqueHow
Idempotency keySend a unique header (e.g. Idempotency-Key) per business action. Payment APIs commonly support this.
Check before createSearch by a business reference (invoice number) first; create only if not found.
UpsertUse an endpoint that creates-or-updates by a unique key.
Use the right methodPUT and DELETE are naturally safe to repeat; POST isn’t (Phase 1).

10Timeouts

Connection timeout

How long to wait for the other side to pick up the phone. Fails fast when the server is down or a firewall blocks the port (Phase 1’s nc check).

Read timeout

How long to wait for the answer after they picked up. Fails when the server is slow, like a huge report or a heavy query.

Synchronous calls in OIC can’t wait forever: if the target is slow, OIC eventually stops waiting and raises a fault, and the caller of your integration has its own limit too. The fix for slow work isn’t a longer timeout; it’s an asynchronous design (next chapter).

11202 Accepted: come back later

The dry cleanerYou hand over a suit. They don’t make you wait in the shop: they give you a token slip and say “come back on Friday”. For long jobs, an API answers 202 Accepted with a job ID, and you check the job’s status later.

Oracle Fusion works exactly like this for bulk loads: you submit a job, get a request ID, then check its status with operations like getESSJobStatus (Part 3.2), or receive a callback when it finishes (a webhook, from Part 3.1). In OIC, the checking part is a While loop with a Wait (Phase 7).

B · Terminal

A pagination loop in 6 lines

page=1; total=0
while true; do
  n=$(curl -s "https://jsonplaceholder.typicode.com/posts?_page=$page&_limit=25" | python3 -c "import sys,json;print(len(json.load(sys.stdin)))")
  [ "$n" -eq 0 ] && break
  total=$((total+n)); echo "page $page: $n posts (total $total)"; page=$((page+1))
done; echo "done: $total posts"
page 1: 25 posts (total 25)
page 2: 25 posts (total 50)
page 3: 25 posts (total 75)
page 4: 25 posts (total 100)
done: 100 posts

Read the Link header (next page’s address)

curl -sI "https://jsonplaceholder.typicode.com/posts?_page=1&_limit=25" | grep -iE "^link|x-total-count"
x-total-count: 100 and a link: header with rel="next" and rel="last"

Choose fields, sort, filter

curl -s "https://jsonplaceholder.typicode.com/posts?userId=1&_sort=id&_order=desc&_limit=3" | python3 -m json.tool

curl -s -o /dev/null -w "%{http_code} in %{time_total}s\n" https://httpbin.org/delay/3   200 in ~3s

15Common mistakes

  1. 1
    Only the first pageYour test data fit in one page; production didn’t. Always loop on hasMore.
  2. 2
    Downloading everything, then filteringFilter with q= or query parameters on the server.
  3. 3
    Retrying a 400It will fail the same way, and may count against your rate limit.
  4. 4
    Blindly retrying a POST after a timeoutCheck first, or use an idempotency key.
  5. 5
    Building Fusion item URLs by handUse the item’s self link.
  6. 6
    All jobs at 00:00Spread schedules to stay under rate limits.
  7. 7

16Self-check

Answer in your head first, then tap to check.

1. Name 4 things to check in API docs before building.

Any four of: base URL, authentication, endpoints, pagination, limits, errors, versioning, sync vs async.

2. A Fusion response says "hasMore": true, "offset": 0, "limit": 500. What’s your next call?

The same call with offset=500.

3. What is a delta sync?

Fetching only records changed since the last run, e.g. with q=LastUpdateDate>'…'.

4. What do fields and onlyData=true do in Fusion?

Return only the listed fields, and drop the links clutter.

5. Which answers should you retry?

Timeouts, 429 (after Retry-After), and 502/503/504 with backoff. Not 4xx like 400, 401, 403, 404.

6. What is exponential backoff with jitter?

Waiting longer after each failure (1s, 2s, 4s…) plus a little randomness, and stopping after a few tries.

7. A POST timed out. Why not just retry?

It may have succeeded; a retry could create a duplicate. Check first or use an idempotency key.

8. What does 202 Accepted mean?

The job was accepted and will finish later; check its status (often via the Location URL).

9. How do you pass a value from one Postman request to the next?

Save it in the Tests tab with pm.environment.set(), then use {{name}} in the next request.

10. Connection timeout vs read timeout?

Connection: waiting for the server to pick up. Read: waiting for the answer after that.

All of it, in one sentence

Real APIs need you to read the docs, page until there’s no more, filter on the server, respect rate limits, retry only what’s temporary (with backoff, and safely for POST), design long jobs asynchronously, and prove it all in Postman with tests before OIC; and Oracle Fusion follows these rules with items, hasMore, q and limit/offset.
