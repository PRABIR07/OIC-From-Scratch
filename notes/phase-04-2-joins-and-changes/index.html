1Why joins exist

Two registers on the deskThe staff register says “Sneha · dept 30”. To know that dept 30 is IT in Bengaluru, you open the department register and look up 30. A join is the database doing that lookup for every row, in one go.

Why not just write “IT, Bengaluru” on every employee row? Because if IT moves to Hyderabad, you’d have to fix hundreds of rows, and you’d miss some. Storing each fact once and linking by keys is called normalisation. The price is that reading needs joins.

2INNER JOIN

SELECT e.first_name, e.last_name, d.dept_name, d.location
FROM   employees   e                        -- e is a table alias
JOIN   departments d                        -- JOIN means INNER JOIN
       ON e.dept_id = d.dept_id             -- the matching rule
ORDER  BY e.emp_id;
FIRST_NAME LAST_NAME DEPT_NAME LOCATION
---------- --------- --------- ---------
Ravi       Kumar     HR        Pune
Priya      Sharma    Finance   Mumbai
Amit       Patel     IT        Bengaluru
Sneha      Iyer      IT        Bengaluru
Arjun      Singh     IT        Bengaluru
Neha       Gupta     Finance   Mumbai
Karan      Mehta     Sales     Delhi
Pooja      Reddy     HR        Pune
Anjali     Nair      Sales     Delhi     ← 9 rows: Vikram and Legal are gone
PieceWhy
employees eA short table alias, so you can write e.dept_id instead of employees.dept_id
e.dept_id, d.dept_idBoth tables have a dept_id column, so you must say which one. Without the prefix: ORA-00918: column ambiguously defined
ON …The rule that decides which rows belong together, almost always foreign key = primary key

INNER means: keep only rows that found a partner on both sides. You’ll also see the old Oracle style, FROM employees e, departments d WHERE e.dept_id = d.dept_id. It gives the same answer, but forget the WHERE and you get every employee paired with every department (10 × 5 = 50 rows, a Cartesian product). Prefer the JOIN … ON style.

3LEFT, RIGHT and FULL OUTER JOIN

The wedding seating listYou need a list of every guest with their table number, including guests who haven’t been given a table yet (show a blank). That’s a LEFT JOIN: everyone from the left list stays, with blanks where no partner was found.

Every employee, department if any

SELECT e.first_name, d.dept_name
FROM   employees e
LEFT   JOIN departments d
       ON e.dept_id = d.dept_id
ORDER  BY e.emp_id;
FIRST_NAME DEPT_NAME
---------- ---------
Ravi       HR
…  (7 more)
Vikram     (null)
Anjali     Sales   10 rows

Which department has nobody?

SELECT d.dept_name
FROM   departments d
LEFT   JOIN employees e
       ON e.dept_id = d.dept_id
WHERE  e.emp_id IS NULL;
DEPT_NAME
---------
Legal

The second query is a classic pattern called an anti-join: LEFT JOIN, then keep only rows where the right side stayed empty. Integrations use it to find “records in A that are missing from B”, for example employees in the HR system who were never created in payroll.

The LEFT JOIN trap. A condition on the right table in the WHERE clause (WHERE d.location = 'Pune') throws away the NULL rows and silently turns your LEFT JOIN back into an INNER JOIN. To filter the right side but keep everyone, put the condition in the ON: ON e.dept_id = d.dept_id AND d.location = 'Pune'.

4Self join: a table joined to itself

The class photoTo label who sits next to whom in a class photo, you look at the same photo twice. A self join reads the same table twice under two aliases. Our manager_id points at another row of employees.
SELECT e.first_name AS employee,
       m.first_name AS manager
FROM   employees e                       -- e = the employee's copy
LEFT   JOIN employees m                  -- m = the manager's copy
       ON e.manager_id = m.emp_id
WHERE  e.dept_id = 30
ORDER  BY e.emp_id;
EMPLOYEE MANAGER
-------- -------
Amit     (null)
Sneha    Amit
Arjun    Amit

LEFT, because top managers have no manager and should still appear. You’ll see this pattern in HR integrations that send a reporting line (“supervisor”) along with each worker.

5Aggregate functions

The bill at the endA restaurant bill doesn’t list every bite: it gives a count of items and a total. Aggregate functions squash many rows into one answer.
SELECT COUNT(*)                AS all_rows,
       COUNT(email)            AS with_email,
       COUNT(DISTINCT dept_id) AS depts_used,
       SUM(salary)             AS total_pay,
       AVG(salary)             AS avg_pay,
       MIN(salary)             AS lowest,
       MAX(salary)             AS highest,
       TO_CHAR(MIN(hire_date), 'YYYY-MM-DD') AS first_hire
FROM   employees;
ALL_ROWS WITH_EMAIL DEPTS_USED TOTAL_PAY AVG_PAY LOWEST HIGHEST FIRST_HIRE
-------- ---------- ---------- --------- ------- ------ ------- ----------
      10          9          4    793000   79300  48000  130000 2017-01-10
FunctionWatch out
COUNT(*)Counts rows, whatever is in them
COUNT(column)Counts only non-NULL values: 9 emails, because Karan has none
COUNT(DISTINCT column)Counts different values: 4 departments (NULL isn’t counted)
SUM, AVG, MIN, MAXAll ignore NULLs. An AVG over values (10, NULL, 20) is 15, not 10

Integrations use this for reconciliation: after loading a file, compare COUNT(*) and SUM(amount) in the target with the file’s trailer record. If they match, nothing was lost.

6GROUP BY: one answer per group

Sorting the postA postman tips the sack onto a table and makes one pile per pin code. Then for each pile he counts the letters. GROUP BY makes the piles; the aggregate function measures each pile.
SELECT dept_id,
       COUNT(*)           AS headcount,
       SUM(salary)        AS total_pay,
       ROUND(AVG(salary)) AS avg_pay
FROM   employees
GROUP  BY dept_id
ORDER  BY dept_id;
DEPT_ID HEADCOUNT TOTAL_PAY AVG_PAY
------- --------- --------- -------
     10         2    143000   71500
     20         2    180000   90000
     30         3    293000   97667
     40         2    107000   53500
(null)          1     70000   70000     ← NULLs form their own pile
The golden rule of GROUP BY. Every column in SELECT must either be inside an aggregate or be listed in GROUP BY. Ask for first_name too, and Oracle answers ORA-00979: not a GROUP BY expression: a pile of three people has no single first name.

Group with a join: names instead of numbers, and Legal counted as 0

SELECT d.dept_name, COUNT(e.emp_id) AS headcount
FROM   departments d
LEFT   JOIN employees e ON e.dept_id = d.dept_id
GROUP  BY d.dept_name
ORDER  BY headcount DESC, d.dept_name;
DEPT_NAME HEADCOUNT
--------- ---------
IT                3
Finance           2
HR                2
Sales             2
Legal             0

Look closely: COUNT(e.emp_id), not COUNT(*). Legal’s row exists (with an empty employee side), so COUNT(*) would say 1. Counting a column from the right table counts only real employees.

7HAVING vs WHERE

Two sievesThe postman first throws away junk mail (before making piles). Then he only delivers piles with at least two letters (after making piles). WHERE filters rows before grouping; HAVING filters groups after.
SELECT d.dept_name, COUNT(*) AS active_staff, ROUND(AVG(e.salary)) AS avg_pay
FROM   employees e
JOIN   departments d ON e.dept_id = d.dept_id
WHERE  e.status = 'ACTIVE'                 -- sieve 1: rows
GROUP  BY d.dept_name
HAVING COUNT(*) >= 2                       -- sieve 2: groups
ORDER  BY avg_pay DESC;
DEPT_NAME ACTIVE_STAFF AVG_PAY
--------- ------------ -------
IT                   3   97667
Finance              2   90000
HR                   2   71500    ← Sales lost Anjali (INACTIVE) in sieve 1, then had only 1 left
WHEREHAVING
FiltersSingle rowsWhole groups
RunsBefore GROUP BYAfter GROUP BY
Can use aggregates?No: WHERE COUNT(*) > 1 is an errorYes: that’s its job

A very common data-quality query uses HAVING to find duplicates: SELECT email, COUNT(*) FROM employee_stg GROUP BY email HAVING COUNT(*) > 1. Run it on a staging table before loading, and you catch duplicate records before they cause unique-constraint errors.

8The order Oracle actually runs a query

We write SELECT first, but the database runs it in a different order. Knowing this order explains half of all SQL error messages.

This fails……because
SELECT salary*12 AS annual … WHERE annual > 1000000WHERE (step 2) runs before the alias is created (step 5): ORA-00904: invalid identifier. Repeat the expression: WHERE salary*12 > 1000000
WHERE COUNT(*) > 1Groups don’t exist yet in step 2. Use HAVING.
ORDER BY annualThis one works: ORDER BY runs after SELECT.

9Subqueries: a query inside a query

Two-step question“Who earns more than average?” is really two questions: first “what’s the average?”, then “who’s above it?”. A subquery answers the inner question first, in brackets, and hands the answer to the outer one.

Single value: above the company average (79300)

SELECT first_name, salary FROM employees
WHERE  salary > (SELECT AVG(salary) FROM employees)
ORDER  BY salary DESC;
FIRST_NAME SALARY
---------- ------
Amit       130000
Priya      120000
Ravi        95000
Sneha       85000

A list: everyone working in Pune or Mumbai

SELECT first_name FROM employees
WHERE  dept_id IN (SELECT dept_id FROM departments WHERE location IN ('Pune', 'Mumbai'))
ORDER  BY emp_id;
FIRST_NAME
----------
Ravi
Priya
Neha
Pooja

EXISTS: departments with at least one person earning over 1 lakh

SELECT d.dept_name FROM departments d
WHERE  EXISTS (SELECT 1 FROM employees e
               WHERE e.dept_id = d.dept_id AND e.salary > 100000)
ORDER  BY d.dept_name;
DEPT_NAME
---------
Finance
IT

The last one is correlated: the inner query uses d.dept_id from the outer row, so it runs once per department. EXISTS only asks “is there at least one?”, and stops at the first match. It’s also NULL-safe, unlike NOT IN (Part 4.1, chapter 9), so NOT EXISTS is the safer way to find missing records.

If a subquery used with = returns more than one row, Oracle stops with ORA-01427: single-row subquery returns more than one row. Use IN when the inner answer can be a list.

10INSERT: adding rows

INSERT INTO employees (emp_id, first_name, last_name, email,
                       job_title, salary, hire_date, dept_id)
VALUES (112, 'Meera', 'Joshi', 'meera.joshi@company.com',
        'Legal Advisor', 88000, DATE '2026-10-16', 50);
1 row inserted.

Always list the columns. Columns you leave out get their DEFAULT (status becomes 'ACTIVE', last_update_date becomes now) or NULL. If someone adds a column to the table later, your statement still works.

INSERT … SELECT: copy many rows in one statement

INSERT INTO employee_stg (emp_id, first_name, last_name, email, job_title, salary, dept_id)
SELECT emp_id, first_name, last_name, email, job_title, salary, dept_id
FROM   employees
WHERE  dept_id = 20;
2 rows inserted.   ← no VALUES: the rows come from the query

11UPDATE and DELETE

Measure twice, cut onceA tailor checks the measurements before cutting the cloth, because a cut can’t be undone. Before any UPDATE or DELETE, run the same WHERE as a SELECT and check the rows.

1 · Check first

SELECT emp_id, salary FROM employees WHERE dept_id = 10;
EMP_ID SALARY
------ ------
   101  95000
   108  48000

2 · Then change exactly those rows

UPDATE employees
SET    salary           = salary * 1.10,       -- 10% raise
       last_update_date = SYSTIMESTAMP          -- so delta queries notice!
WHERE  dept_id = 10;
2 rows updated.        ← the count should match your SELECT

DELETE

DELETE FROM employees WHERE emp_id = 112;
1 row deleted.
Forget the WHERE and every row changes. UPDATE employees SET salary = 50000; gives everyone the same salary. DELETE FROM employees; empties the table. Both are allowed, and both are silent. Chapter 12 shows how to undo them, if you haven’t committed.
DELETETRUNCATE TABLE
RemovesRows matching WHERE (or all)Always all rows
Undo with ROLLBACK?Yes, until COMMITNo: it’s DDL, auto-commits
Speed on big tablesSlower: logs every rowVery fast
Typical useRemove specific recordsEmpty a staging table before a new load

Deleting a parent that still has children fails: DELETE FROM departments WHERE dept_id = 30 → ORA-02292: integrity constraint (…EMP_DEPT_FK) violated - child record found. The foreign key is protecting you. In HR systems, people are rarely deleted anyway: they’re ended (status INACTIVE, an end date), so history stays.

12Transactions: COMMIT and ROLLBACK

A bank transferMoving ₹5,000 from your account to a friend’s is two steps: take it from you, add it to them. If the system crashes between the two, the money must not vanish. Either both happen, or neither. That bundle is a transaction.
StatementDoes
COMMITSaves every change since the last commit. Other sessions can now see them. Can’t be undone.
ROLLBACKThrows away every change since the last commit.
SAVEPOINT a / ROLLBACK TO aA bookmark inside a transaction: undo back to it, keep what came before.

Undo a mistake

UPDATE employees SET salary = 50000;          -- oops, no WHERE
10 rows updated.
ROLLBACK;
Rollback complete.
SELECT salary FROM employees WHERE emp_id = 103;
130000                                        ← saved, because nothing was committed

Locks: while your transaction has updated a row but not committed, another session that tries to update the same row waits. A forgotten uncommitted session can make an integration hang. Commit or roll back promptly.

In OIC: each database adapter call normally commits its own work when it succeeds. So if an integration inserts a header in one call and lines in a second call, and the second fails, the header stays. When steps must be all-or-nothing, put them in one stored procedure (Part 4.3) and let it commit once at the end.

13MERGE: insert or update in one statement

The school admission deskA form arrives. If the student already has a file, the clerk updates it. If not, the clerk opens a new file. Either way, there’s never a second file for the same student. That’s an upsert, and in SQL it’s called MERGE.
MERGE INTO employees e                                   -- target
USING (SELECT * FROM employee_stg
       WHERE  process_status = 'NEW') s                  -- source
ON    (e.emp_id = s.emp_id)                              -- the matching rule
WHEN MATCHED THEN UPDATE SET
      e.first_name = s.first_name, e.last_name = s.last_name,
      e.email      = s.email,      e.job_title = s.job_title,
      e.salary     = s.salary,     e.dept_id   = s.dept_id,
      e.last_update_date = SYSTIMESTAMP
WHEN NOT MATCHED THEN INSERT
      (emp_id, first_name, last_name, email, job_title, salary, hire_date, dept_id)
      VALUES (s.emp_id, s.first_name, s.last_name, s.email, s.job_title,
              s.salary, TRUNC(SYSDATE), s.dept_id);
3 rows merged.

The result

SELECT emp_id, first_name, job_title, salary FROM employees
WHERE  emp_id IN (104, 108, 111) ORDER BY emp_id;
EMP_ID FIRST_NAME JOB_TITLE                    SALARY
------ ---------- ---------------------------- ------
   104 Sneha      Senior Integration Developer  92000    ← updated
   108 Pooja      HR Executive                  48000    ← updated (same values)
   111 Rahul      Integration Developer         75000    ← inserted

Now run the MERGE a second time. It says 3 rows merged again, but there’s still only one Rahul. Remember Part 3.4’s retry problem: a blind INSERT run twice creates duplicates; a MERGE run twice gives the same result. That makes MERGE idempotent, and that’s why integrations love it.

Rules: the ON columns should identify one row (a key), and you can’t UPDATE the columns used in ON (ORA-38104). If two source rows match the same target row, Oracle stops with ORA-30926: unable to get a stable set of rows: remove duplicates from the source first (chapter 7’s HAVING query).

14Sequences and identity columns

The token machineAt a bank, the token machine gives the next number to whoever presses the button, even if a hundred people press at once, and never gives the same number twice. A sequence is that machine for primary keys.

A sequence

CREATE SEQUENCE emp_seq START WITH 200;

SELECT emp_seq.NEXTVAL FROM dual;   200
SELECT emp_seq.NEXTVAL FROM dual;   201
SELECT emp_seq.CURRVAL FROM dual;   201

INSERT INTO employees (emp_id, last_name, hire_date)
VALUES (emp_seq.NEXTVAL, 'Test', SYSDATE);

An identity column (Oracle 12c+)

CREATE TABLE integration_log (
  log_id NUMBER GENERATED ALWAYS
         AS IDENTITY PRIMARY KEY,
  …
);

INSERT INTO integration_log (run_name, status)
VALUES ('daily-sync', 'OK');
-- log_id fills itself: 1, 2, 3…

Our integration_log table uses an identity column. Numbers can have gaps (a rolled-back insert still used its number), so never rely on IDs being continuous. And if you need the new ID back in OIC after an insert, a stored procedure with an OUT parameter is the cleanest way (Part 4.3).

15Views and indexes

A view: a saved query

Like a saved filter in your email. It stores the question, not a copy of the data, so it always shows current rows.

An index: the book’s index

To find “MERGE” in a 500-page book you don’t read every page; you check the index at the back. An index lets the database jump straight to the rows.

A view that hides the join

CREATE OR REPLACE VIEW emp_details_v AS
SELECT e.emp_id, e.first_name, e.last_name, e.job_title, e.salary,
       d.dept_name, d.location, e.last_update_date
FROM   employees e
LEFT   JOIN departments d ON e.dept_id = d.dept_id;

SELECT first_name, dept_name FROM emp_details_v WHERE location = 'Pune';
FIRST_NAME DEPT_NAME
---------- ---------
Ravi       HR
Pooja      HR

Views are handy for integrations: give OIC a view with exactly the columns it needs, and the integration never has to know the joins behind it. You can also grant access to a view without giving access to the whole table.

An index for the nightly delta query

CREATE INDEX emp_last_update_ix ON employees (last_update_date);

With a million rows, WHERE last_update_date > … without an index reads every row (a “full table scan”); with the index it jumps to the recent ones. Primary keys and unique constraints get an index automatically. Indexes speed up reading but slow down inserts and updates a little, so add them for columns you filter or join on often. To see how Oracle plans to run a query, use Explain Plan (F10 in FreeSQL).

A sneaky one: WHERE UPPER(last_name) = 'KUMAR' can’t use a normal index on last_name, because the function changes the value. Oracle supports function-based indexes for that: CREATE INDEX … ON employees (UPPER(last_name)).

19Self-check

Answer in your head first, then tap to check.

1. INNER vs LEFT JOIN, in one line each?

INNER keeps only rows with a match on both sides. LEFT keeps every row from the first table, with NULLs where no match was found.

2. How do you find departments that have no employees?

LEFT JOIN employees and keep rows WHERE e.emp_id IS NULL (an anti-join), or use NOT EXISTS.

3. COUNT(*) vs COUNT(email)?

COUNT(*) counts rows; COUNT(email) counts only rows where email isn’t NULL.

4. Why does SELECT dept_id, first_name, COUNT(*) … GROUP BY dept_id fail?

first_name is neither aggregated nor in GROUP BY: ORA-00979.

5. WHERE vs HAVING?

WHERE filters rows before grouping; HAVING filters groups after grouping and can use aggregates.

6. Why can’t WHERE use a column alias from SELECT?

WHERE runs before SELECT, so the alias doesn’t exist yet. ORDER BY runs after, so it can.

7. You ran an UPDATE without WHERE and haven’t committed. What now?

ROLLBACK. Every change since the last commit is undone.

8. DELETE vs TRUNCATE?

DELETE is DML: can use WHERE and can be rolled back. TRUNCATE is DDL: removes all rows, fast, auto-commits, can’t be rolled back.

9. Why is MERGE better than INSERT for integrations?

It inserts new rows and updates existing ones, so running it twice doesn’t create duplicates: it’s idempotent.

10. A nightly delta query got slow as the table grew. First thing to check?

Whether there’s an index on the column in the WHERE, such as last_update_date (look at the explain plan).

All of it, in one sentence

Joins stitch tables together on their keys (INNER for matches only, LEFT/RIGHT/FULL to keep the unmatched), GROUP BY with aggregates and HAVING turn rows into totals, subqueries answer two-step questions, and INSERT, UPDATE, DELETE and idempotent MERGE change data inside transactions that you COMMIT or ROLLBACK as one.
