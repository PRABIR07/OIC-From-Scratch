Actions: teaching your integration to think

Phase 6 · OIC Basics. Your first integration always did the same thing: fetch, map, reply. Real integrations must decide, remember, repeat, report and protect themselves. That’s what actions are for. We learn each one with a story, then add them to your integration in two step-by-step labs.

1What actions are

A recipe is more than ingredientsA recipe doesn’t only say “take rice, add water”. It says “if the rice is old, soak it longer”, “stir every 5 minutes”, “note the time”, “tell everyone when it’s ready”, “if it burns, start again”. Triggers, invokes and maps are the ingredients. Actions are the instructions: decide, repeat, remember, report, recover.

You add an action exactly like an invoke: hover over a line on the canvas, click +, and choose it from the Actions list.

2Assign: giving your integration a memory

The sticky noteWhile cooking you jot “started at 7:10” on a sticky note, so you can check it later. A variable is a labelled sticky note inside one run of the integration, and Assign is the action that writes on it.
Box in AssignWhat to put
+ (add)Choose the type. For beginners it’s String (text). Numbers are stored as text too, and compared with functions when needed.
VariableA name. A good habit: start with v_, like v_status, so it never looks like a data field
OperationAlways = for String: “this variable becomes…”
ValueText in single quotes, like 'FOUND', or a value dragged from Sources, or an expression

Once assigned, the variable appears in the Sources list of later maps and Switch conditions (often under a $ sign, like $v_status). Assign again later to change it.

Where a variable can be seen: a variable created inside a loop or a scope is only visible inside it. If you need it afterwards, create it with an Assign before the loop or scope, and just update it inside.

3Switch: choosing a path

The railway signalAt a junction, the signal checks the train: goods train → left track; passenger train → right track; anything else → the main line. Each train takes exactly one track. Switch works the same way: it checks conditions from top to bottom, and the run follows the first route that’s true. If none is true, it takes Otherwise.
PartWhat it is
RouteA branch with a condition. A new Switch starts with Route 1 and Otherwise. Add more routes from the Switch’s actions menu
ConditionBuilt in Configure Route: a Value (drag a field), an Operator (=, >, !=…), and a second Value (like 10 or 'IN'). Combine several with “Add condition”
OtherwiseRuns when no route matched. Always think about what should happen here

Behind the screen, a condition is just XPath from Phase 2, like $id > 10. The developer view of the condition editor shows it.

4Log: the integration’s diary

The captain’s logbookA ship’s captain writes in the logbook: “10:00 left port. 14:30 storm, changed course.” Later, anyone can read what happened and why. The Log action (also called Logger) writes a line into the run’s activity stream, so when you open an instance later, you can read its story.
BoxWhat to put
Logging modeAlways (written on every run) or When tracing level is set to Audit (only when you’re investigating)
MessageFixed text, or a message built from data, like concat('Fetched user ', name)

Good log messages

“Fetched user 3, Clementine Bauch” · “Skipping order 501: status CANCELLED” · “Loaded 250 of 250 invoices”

Bad log messages

“here” · “step 2 done” · a full payload with passwords or salaries in it (logs are read by many people, Part 3.3)

A good log line answers, months later: what happened, to which record, and why.

5Notification: telling a human

The doorbellMost of the time, integrations run silently. But some moments need a person: “The nightly bank file failed”, “A big order just arrived”. Notification is the integration ringing a person’s doorbell, by sending an email.
BoxWhat to put
ToAn email address, typed or taken from the data. Several addresses are separated by commas
FromLeave as default (a no-reply address), unless your admin approved a sender in Settings → Notifications
SubjectPlain text, or built from data
BodyText or simple HTML. Insert data with parameters in curly brackets, like User {userName} was fetched.
ParametersClick +, give a name (userName) and map a value to it

Limits matter: emails count against a daily allowance (your home page shows it, “0 of 100”), and one email can’t be bigger than about 1 MB. So notify people about exceptions, not every successful run; nobody reads 500 emails a day.

6For Each: once for every item

The teacher and the notebooksA teacher has a pile of 40 notebooks. She picks up the first, checks it, puts it aside, picks up the next… until the pile is empty. She doesn’t write 40 different instructions: one instruction, repeated for each notebook. That’s the For Each action.
BoxWhat to put
Repeating ElementDrag the list from Sources: the element that repeats (it shows a repeat sign in the tree)
Current Element NameA nickname for “the item I’m holding right now”, like currentPost. Inside the loop, use it in maps and logs
Process items in parallelHandle several items at the same time. Leave it off while learning: one by one is easier to follow

This is how OIC processes real batches: every line of an invoice file, every employee in a list, every order from an API page (Part 3.4’s pagination). Remember the warning from Part 4.6, though: calling a system once per item is slow for big lists. Loop for logic; send big batches in one call when the target allows it.

7While: repeat until something changes

Stirring the milkYou don’t stir milk “10 times”. You stir while it hasn’t boiled. The number of rounds isn’t known in advance. While repeats its steps as long as a condition is true.
For EachWhile
RepeatsOnce per item in a listAs long as a condition is true
You know how many times?Yes: the list’s lengthNo
Classic use in OICProcess every record in a responsePaging (while hasMore is true, Part 3.4) and polling a job (while status is RUNNING, wait and check again)
The infinite loop trap. If nothing inside the loop ever changes the condition, it runs forever. Always update something inside: a counter (v_page = v_page + 1) or a status from the latest call. And add a safety limit, like “and v_attempts < 20”.

8Scope and fault handlers: the safety net

The trapeze netA trapeze artist performs over a net. If she falls, she lands safely, and the show goes on. A Scope is a box you put around some steps; its fault handler is the net. If any step inside fails, OIC jumps to the handler instead of crashing the whole run.

Inside a scope’s Fault Handlers, the Default Handler catches any error. In it you typically log what went wrong, notify support, and then either recover (for example, reply “user not available” instead of an error) or Re-throw Fault so the run is marked failed and appears in Observability → Errors.

Fault handling is a big topic, and it gets a full chapter in Phase 7. For now, remember the idea: risky steps (calls to other systems) go inside a scope with a net under them.

9Throw New Fault and Wait

Throw New Fault: the emergency chain

Stops the run on purpose with your own error: a Code (like INVALID_ID), a Reason (“User id must be 1 to 10”) and Details. Use it when the data is wrong and continuing would be pointless or harmful. It’s OIC’s twin of PL/SQL’s RAISE_APPLICATION_ERROR (Part 4.6).

Wait: come back later

Pauses the run for a number of seconds. Used inside a While to check a long job’s status every few minutes (Part 3.4, 202 Accepted), or to slow down before a retry when an API says 429.

Throwing a fault isn’t “breaking” the integration: it’s failing clearly. A run that stops with “INVALID_ID: User id must be 1 to 10” is far easier to support than one that quietly sends a half-empty reply.

11Lab A: make Get User By Id smarter

We’ll upgrade your integration from Part 6.3 so that it:

  1. refuses ids above 10 with a clear error (Switch + Log + Throw New Fault),
  2. remembers what happened in a variable (Assign),
  3. writes a diary line for every good fetch (Log).

Part 1 · Open it for editing

  1. 1
    Deactivate☰ → Projects → My First Project. On Get User By Id, click Actions (⋯) → Deactivate, and confirm.
    Why: an Active integration can’t be edited.
    ✓ You’ll see: status changes to Configured.
  2. 2
    Open the canvasClick the integration’s name (or Actions → Edit).
    ✓ You’ll see: GetUser → Map → FetchUser → Map.

Part 2 · Assign a status

  1. 3
    Add Assign after the triggerHover on the line right below GetUser, click + → Actions → Assign.
  2. 4
    Name itName: SetStatus.
  3. 5
    Add the variableClick +, choose String. Variable: v_status. Value: 'STARTED' (with the single quotes).
    ✓ You’ll see: one row: v_status = 'STARTED'. Close the panel.

Part 3 · The Switch

  1. 6
    Add a Switch after AssignHover on the line below SetStatus → + → Actions → Switch.
    ✓ You’ll see: two branches: Route 1 (or a branch with an empty condition) and Otherwise.
  2. 7
    Configure Route 1Click Route 1 → Edit. In Configure Route: upper Value: drag id from GetUser Request → Template Parameters. Operator: >. Lower Value: 10. Name the route InvalidId. Save/close.
    ✓ You’ll see: the route shows a condition like id > 10.
  3. 8
    Move the normal path into OtherwiseThe existing Map → FetchUser → Map must run only in the Otherwise branch. If OIC placed them after the Switch, drag each one into the Otherwise branch (or use their move/cut options), in the same order.
    ✓ You’ll see: Otherwise contains Map → FetchUser → Map; InvalidId is empty.

Part 4 · The bad-id branch

  1. 9
    Log the problemInside InvalidId, click + → Actions → Log. Name: LogInvalidId. Logging mode: Always. Message: build concat('Invalid user id requested: ', id) (drag id from Sources into the expression).
  2. 10
    Throw the faultBelow the Log, click + → Actions → Throw New Fault. Name: InvalidIdFault. Code: 'INVALID_ID'. Reason: 'User id must be between 1 and 10'. Leave Details empty.
    ✓ You’ll see: InvalidId: Log → Throw New Fault.

Part 5 · The good-path diary line

  1. 11
    Log after FetchUserIn Otherwise, between FetchUser and the last Map, click + → Actions → Log. Name: LogFetched. Mode: Always. Message: concat('Fetched user ', id, ': ', name), dragging id and name from FetchUser Response.
  2. 12
    Update the statusBelow LogFetched, add an Assign named SetFound: choose the existing variable v_status, Value 'FOUND'.

Part 6 · Save, activate, test

  1. 13
    Check errors and saveFix any red error icon, click Save, then Back.
  2. 14
    ActivateActions (⋯) → Activate → tracing Production → Activate. Refresh until Active.
  3. 15
    Good idActions → Run, id = 3 → Run.
    ✓ You’ll see: status 200, user Clementine Bauch, and in the activity stream a line “Fetched user 3: Clementine Bauch”.
  4. 16
    Bad idRun again with id = 25.
    ✓ You’ll see: an error response instead of 200, the log line “Invalid user id requested: 25”, and the fault INVALID_ID in the activity stream. No call was made to JSONPlaceholder.

Compare with Part 6.3: id 25 used to reach JSONPlaceholder and fail with a confusing 404. Now it fails early, with your clear message. That’s professional integration design.

  3. 3

  2. 6

  4. 8

  2. 10

  2. 13

Why ten lines? User 1 has exactly 10 posts on JSONPlaceholder (open https://jsonplaceholder.typicode.com/posts?userId=1 in your browser and count). The For Each ran its inside steps once per post. Try id 2: ten more, all different titles.

13Common mistakes

What went wrongFix
Assign value FOUND without quotesText needs single quotes: 'FOUND'. Without them, OIC looks for a field called FOUND
Switch never takes your routeCheck the condition and its types; open the developer view to read the real expression
Forgot the Otherwise pathDecide what happens when no route matches, even if it’s just a Log
Logging whole payloads with personal dataLog ids and short messages, not salaries, passwords or full records
One email per successful runNotify on exceptions only; mind the daily email limit
Inside the loop, mapped from the whole listUse the current element (currentPost), not the list
A While loop that never endsChange the condition inside the loop, and add a maximum-attempts check
Variable “disappears” after a loopCreate it with Assign before the loop; only update it inside

15Self-check

Answer in your head first, then tap to check.

1. You need to remember “how many records failed” during a run. Which action?

Assign (a variable).

2. A Switch has routes A (true) and B (also true). Which runs?

Only A: the first true route wins. Otherwise runs only when none is true.

3. For Each or While: process every line of an invoice file?

For Each: you have a list of known items.

4. For Each or While: keep calling an API page by page until hasMore is false?

While: you don’t know how many pages in advance.

5. What’s the risk with While, and how do you prevent it?

An infinite loop. Change the condition inside the loop and add a maximum-attempts check.

6. Why Throw New Fault for id 25 instead of letting the API return 404?

It fails early, with a clear code and reason, without a useless call to the other system.

7. What’s a Scope’s fault handler for?

A safety net: if a step inside fails, it runs instead, to log, notify, recover or re-throw.

8. Inside a For Each, where do you take fields from?

From the current element (e.g. currentPost), not the whole list.

All of it, in one sentence

Actions make an integration think: Assign remembers, Switch chooses one path, Log writes the diary, Notification tells people, For Each and While repeat, Scope with a fault handler catches failures, and Throw New Fault stops clearly when the data is wrong.
