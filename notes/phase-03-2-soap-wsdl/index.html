SOAP & WSDL in depth

1Why SOAP still matters

Registered postFor a birthday wish you send a WhatsApp. For a legal notice you send registered post: a fixed format, a signature, proof of delivery. SOAP (Simple Object Access Protocol) is the registered post of APIs: strict, formal, and built for enterprises that care about contracts more than convenience.

A strict contract

The WSDL defines every field and type. Both sides can generate code from it and validate every message.

Built-in standards

Security (WS-Security), reliable delivery, attachments: all defined as add-on standards.

Still everywhere

Oracle Fusion’s bulk loads, banking gateways, government systems, SAP and older ERPs.

In OIC you’ll use SOAP mostly to call these systems, for example Oracle Fusion’s ErpIntegrationService to load thousands of invoices at once (Phase 8).

2The envelope, part by part

An official letterAn official letter has an outer envelope, a cover sheet with reference numbers and stamps, and the letter itself. If something’s wrong, you get back a formal rejection slip. A SOAP message has exactly these four parts.
Where does the request element’s name come from? Not from your imagination: the WSDL says exactly what to put inside the Body. That’s chapter 4.

3SOAP 1.1 vs SOAP 1.2

There are two versions in use. They look almost the same, but mixing them up gives confusing errors, so check which one a service uses.

SOAP 1.1SOAP 1.2
Envelope namespacehttp://schemas.xmlsoap.org/soap/envelope/http://www.w3.org/2003/05/soap-envelope
Content-Typetext/xml; charset=utf-8application/soap+xml; charset=utf-8
Operation hintSeparate SOAPAction headeraction= inside the Content-Type
Fault fieldsfaultcode, faultstring, detailCode, Reason, Detail
How commonVery common, including many Oracle servicesCommon in newer services

Quick tell: look at the envelope’s namespace. xmlsoap.org means 1.1; w3.org/2003/05 means 1.2. A WSDL can offer both versions as two separate bindings.

4A WSDL, section by section

The full restaurant fileImagine the restaurant gave you its whole file: the ingredient list, each dish’s order slip, the menu, how to order (phone or counter) and the address. A WSDL (Web Services Description Language, “wiz-dull”) is that file, in five sections.

tns: means “this namespace”, the WSDL’s own targetNamespace. It’s how one section points at a name defined in another section.

5Following the chain

A treasure huntEach clue points to the next one. A WSDL is read as a chain of references: start at the address and follow the names until you reach the actual XML you must send. Once you can follow this chain, you can read any WSDL, however big.

6document/literal (and the others)

The binding’s style and use decide how the Body looks. You’ll see these words in WSDLs and in OIC’s SOAP adapter.

CombinationThe Body containsHow common
document / literalExactly the XML element defined in types, nothing extraThe modern standard; easy to validate
document / literal wrappedThe same, where the element is named after the operation (GetEmployee…)Very common, including our practice WSDL
rpc / literalAn element named after the operation, wrapping each partOlder services
rpc / encodedExtra type labels on every valueLegacy; avoid

Rule of thumb: you’ll almost always meet document/literal. Literal means “the Body is literally what the XSD describes”, which is why you can validate a request with the XSD from the types section, exactly like Phase 2.

7The SOAPAction header

The department name on the envelopeOne office address can receive letters for many departments. Writing “Attn: Payroll” on the envelope gets it to the right desk without opening it. In SOAP 1.1, the SOAPAction header tells the server which operation you’re calling, before it reads the Body.

Its exact value comes from the binding’s <soap:operation soapAction="…"/>. Some services ignore it, some require it exactly, and some want an empty "". A wrong SOAPAction is a common cause of “operation not found” faults. In SOAP 1.2 the same value moves into the Content-Type: application/soap+xml; action="…".

8Faults: how SOAP says “no”

The rejection slipWhen an office rejects your application, you get a formal slip: a category (your mistake or ours), a reason in words, and details like a reference code. A SOAP Fault is that slip, delivered inside the Body, usually with HTTP status 500.
faultcodeMeans
Client (1.2: Sender)Your message was wrong: fix the request (like a 4xx)
Server (1.2: Receiver)Their side failed: retry later or contact them (like a 5xx)
VersionMismatchWrong SOAP envelope namespace (1.1 vs 1.2)
MustUnderstandA Header element marked mandatory wasn’t understood
The trap: the HTTP code is 500 even when it’s your mistake. So with SOAP, never judge by the HTTP code alone: read the faultcode and faultstring.

9WS-Security: credentials in the Header

The signed cover sheetInstead of showing ID at the gate, the letter’s cover sheet carries the sender’s name, a signature and a date stamp, so the letter proves itself wherever it goes. WS-Security puts credentials inside the SOAP Header instead of (or as well as) the HTTP headers.

WS-Security can also sign parts of the message (proving nothing changed) and encrypt them. In practice, most services you’ll meet use either HTTP Basic Auth over HTTPS, or a UsernameToken like the one above. OIC can add either for you.

10Big files: MTOM

XML can only hold text, so a file inside a SOAP message must be converted to text with Base64, which makes it about a third bigger. For large files, MTOM sends the file as a separate part next to the XML (like a parcel with a letter taped to it) and the XML just points to it.

You’ll meet this in Oracle Fusion bulk loads: the data file (a zipped CSV) goes up as Base64 content inside a SOAP call. That’s why Phase 2’s CSV and Base64 both matter here.

11SOAP in Oracle Fusion

Oracle Fusion Applications publish many SOAP services. Their WSDLs live on your Fusion host, and you open one by adding ?WSDL:

Operation (examples)Used for
importBulkDataUpload a zipped data file and start the import in one call (FBDI, Phase 8)
getESSJobStatusCheck whether a background job finished
downloadESSJobExecutionDetailsDownload a finished job’s log and output files

Exact operations change between Fusion releases, so always open your own instance’s WSDL rather than copying a list from the internet. You’ll practise reading it with the same chain from chapter 5.

14Common mistakes

  1. 1
    Mixing SOAP 1.1 and 1.2A 1.2 envelope with text/xml, or the other way round, gives a VersionMismatch or 415.
  2. 2
    Wrong or missing SOAPActionCopy it exactly from the binding.
  3. 3
    Wrong namespace on the Body elementRight names, wrong surname: the server says the element is unexpected.
  4. 4
    Judging by HTTP 500 aloneRead the faultcode: it may be your mistake.
  5. 5
    Using a WSDL from the internetUse your own instance’s WSDL: versions differ.
  6. 6
    Element orderXSD sequence means order matters. Swapping two fields makes the message invalid.

15Self-check

Answer in your head first, then tap to check.

1. Name the four parts of a SOAP message.

Envelope, Header (optional), Body (required), and Fault (inside the Body, on errors).

2. How do you tell SOAP 1.1 from 1.2 at a glance?

The envelope namespace: xmlsoap.org is 1.1; w3.org/2003/05 is 1.2.

3. Name the five WSDL sections and the question each answers.

types (data shapes), message (in/out), portType (which operations), binding (how), service (where).

4. Starting from the service, what’s the chain to the Body element?

service/port → binding → portType operation → input message → part element → the element in types.

5. Where does the SOAPAction value come from?

The binding’s soap:operation soapAction attribute.

6. A fault arrives with HTTP 500 and faultcode Client. Whose problem?

Yours: the request was wrong. The 500 is just how SOAP returns faults.

7. What does document/literal mean for the Body?

The Body contains exactly the element defined in types, so it can be validated with that XSD.

8. Where does WS-Security put the username?

In the SOAP Header, inside wsse:Security / wsse:UsernameToken.

All of it, in one sentence

A SOAP call POSTs an XML Envelope with an optional Header and one element in the Body; its shape, operations, binding and address all come from the WSDL, which you read as a chain from service back to types; errors return as a Fault, and credentials can travel in the Header with WS-Security.
