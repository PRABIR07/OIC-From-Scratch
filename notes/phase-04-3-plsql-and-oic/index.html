1Why PL/SQL

One question vs a recipe“How much rice is in the jar?” is one question: that’s SQL. “Check the rice; if there’s less than a cup, add it to the shopping list; then cook it for 15 minutes; if it burns, start again” is a recipe, with steps, decisions and what to do when something goes wrong. PL/SQL (Procedural Language/SQL) is Oracle’s recipe language, and it runs inside the database.

Steps & decisions

Variables, IF, loops: things plain SQL can’t do.

All-or-nothing

Several statements, one COMMIT. If any step fails, undo them all (Part 4.2, ch. 12).

One call from OIC

Instead of five adapter calls across the network, OIC calls one stored procedure that does all five next to the data.

On OIC projects you’ll mostly call procedures that a database developer wrote, and sometimes write small ones yourself for staging and logging. Either way, you must be able to read them.

2A PL/SQL block, part by part

Hello, PL/SQL

BEGIN
  DBMS_OUTPUT.PUT_LINE('Hello from inside the database');
END;
/
Hello from inside the database

DBMS_OUTPUT.PUT_LINE prints a line, like console.log or OIC’s Logger action. In FreeSQL, run blocks with Run Script (F5): the printed lines appear in the Script Output, followed by PL/SQL procedure successfully completed. In SQL*Plus or SQL Developer, run SET SERVEROUTPUT ON first. It’s only for testing: OIC never sees this output. The / on its own line tells the tool “the block ends here, run it”, because a block contains many semicolons.

3Variables and SELECT INTO

Labelled bowlsBefore cooking you set out bowls and label them: “chopped onion”, “2 cups water”. A variable is a labelled bowl that holds one value while the recipe runs.
DECLARE
  v_name   employees.first_name%TYPE;     -- same type as the column
  v_salary employees.salary%TYPE;
  c_bonus  CONSTANT NUMBER := 0.10;       -- a value that never changes
BEGIN
  SELECT first_name, salary
  INTO   v_name, v_salary                  -- put the answer in the bowls
  FROM   employees
  WHERE  emp_id = 104;

  DBMS_OUTPUT.PUT_LINE(v_name || ' earns ' || v_salary
                       || ', bonus ' || v_salary * c_bonus);
END;
/
Sneha earns 85000, bonus 8500
PieceMeans
v_name VARCHAR2(30);Declare a variable with a type. Prefix v_ is a habit, so variables never clash with column names.
:=Assign a value (= is only for comparing)
%TYPE“The same type as this column”. If the column grows from 30 to 50 characters, your code adapts.
%ROWTYPEA variable shaped like a whole row: r employees%ROWTYPE; then r.first_name, r.salary…
SELECT … INTOMust return exactly one row. None: NO_DATA_FOUND. Two or more: TOO_MANY_ROWS (chapter 6)

4IF and CASE

DECLARE
  v_salary employees.salary%TYPE;
  v_band   VARCHAR2(10);
BEGIN
  SELECT salary INTO v_salary FROM employees WHERE emp_id = 105;

  IF v_salary >= 100000 THEN
    v_band := 'A';
  ELSIF v_salary >= 70000 THEN            -- ELSIF, not ELSEIF!
    v_band := 'B';
  ELSE
    v_band := 'C';
  END IF;

  DBMS_OUTPUT.PUT_LINE('Arjun is in band ' || v_band);
END;
/
Arjun is in band B

It’s the same logic as SQL’s CASE (Part 4.1, ch. 14), but IF can run whole statements in each branch: update a table, call a procedure, raise an error. That’s exactly what OIC’s Switch action does inside an integration. PL/SQL also has a CASE … END CASE; statement for long lists of choices.

5Loops and cursors

Dealing cardsA dealer takes one card from the top, gives it to the next player, and repeats until the deck is empty. A cursor is a query whose rows you take one at a time; a cursor FOR loop does the taking for you.

Cursor FOR loop: the one you’ll use most

BEGIN
  FOR r IN (SELECT first_name, salary
            FROM   employees
            WHERE  dept_id = 30
            ORDER  BY emp_id) LOOP
    DBMS_OUTPUT.PUT_LINE(r.first_name || ': ' || r.salary);
  END LOOP;
END;
/
Amit: 130000
Sneha: 85000
Arjun: 78000

Counting loop

BEGIN
  FOR i IN 1 .. 3 LOOP
    DBMS_OUTPUT.PUT_LINE('Attempt ' || i);
  END LOOP;
END;
/
Attempt 1
Attempt 2
Attempt 3

WHILE loop: backoff from Part 3.4

DECLARE
  v_wait NUMBER := 1;
BEGIN
  WHILE v_wait <= 8 LOOP
    DBMS_OUTPUT.PUT_LINE('wait ' || v_wait || 's');
    v_wait := v_wait * 2;
  END LOOP;
END;
/
wait 1s
wait 2s
wait 4s
wait 8s

The cursor FOR loop opens the cursor, fetches each row into r, and closes it, all automatically. You may meet the long form in older code (CURSOR c IS …; OPEN c; FETCH c INTO …; EXIT WHEN c%NOTFOUND; CLOSE c;): it does the same thing by hand. And OIC’s For-Each and While actions are these loops, at the integration level.

6Exceptions: when something goes wrong

The kitchen fire drillA good kitchen has a plan for each problem: the gas runs out → use the induction plate; the dish burns → start again; a fire → stop everything and call for help. The EXCEPTION section is that plan. When an error happens in BEGIN, Oracle jumps straight to EXCEPTION and looks for a matching handler.
DECLARE
  v_name employees.first_name%TYPE;
BEGIN
  SELECT first_name INTO v_name FROM employees WHERE emp_id = 999;
  DBMS_OUTPUT.PUT_LINE('Found ' || v_name);           -- never reached
EXCEPTION
  WHEN NO_DATA_FOUND THEN
    DBMS_OUTPUT.PUT_LINE('No employee 999');
  WHEN TOO_MANY_ROWS THEN
    DBMS_OUTPUT.PUT_LINE('More than one row');
END;
/
No employee 999
Named exceptionErrorHappens when
NO_DATA_FOUNDORA-01403SELECT INTO found no row
TOO_MANY_ROWSORA-01422SELECT INTO found more than one row
DUP_VAL_ON_INDEXORA-00001A primary key or unique value already exists
VALUE_ERRORORA-06502A value doesn’t fit (too long, not a number)
ZERO_DIVIDEORA-01476Division by zero
OTHERSanythingCatches every error not handled above. Always last.

Raising your own errors

IF p_percent > 50 THEN
  RAISE_APPLICATION_ERROR(-20002, 'Raise must be between 0 and 50 percent');
END IF;
ORA-20002: Raise must be between 0 and 50 percent
ORA-06512: at line 2          ← ORA-06512 says WHERE it happened

Your own error numbers must be between −20000 and −20999. This is how a procedure tells OIC “this is a business error”: the code and message arrive in the integration’s fault, and the fault handler can decide what to do (Phase 7).

The worst line in PL/SQL: WHEN OTHERS THEN NULL; It catches every error and does nothing, so the procedure “succeeds”, OIC reports success, and the data is silently wrong. If you catch OTHERS, log it and re-raise it with RAISE; (chapter 10). SQLCODE and SQLERRM give you the error number and message to log.

7Stored procedures

The recipe card in the drawerOnce a recipe works, you write it on a card, give it a name, and keep it in the drawer. Anyone can say “make the dal” and pass in how many people to serve. A stored procedure is a named block saved in the database, with parameters going in and out.
CREATE OR REPLACE PROCEDURE give_raise (
  p_emp_id     IN  employees.emp_id%TYPE,     -- IN: the caller gives it
  p_percent    IN  NUMBER,
  p_new_salary OUT employees.salary%TYPE      -- OUT: we hand it back
) AS
BEGIN
  IF p_percent NOT BETWEEN 0 AND 50 THEN
    RAISE_APPLICATION_ERROR(-20002, 'Raise must be between 0 and 50 percent');
  END IF;

  UPDATE employees
  SET    salary = ROUND(salary * (1 + p_percent / 100), 2),
         last_update_date = SYSTIMESTAMP
  WHERE  emp_id = p_emp_id
  RETURNING salary INTO p_new_salary;           -- read the new value back

  IF SQL%ROWCOUNT = 0 THEN                       -- how many rows did that touch?
    RAISE_APPLICATION_ERROR(-20001, 'Employee ' || p_emp_id || ' not found');
  END IF;
END give_raise;
/
Procedure GIVE_RAISE compiled

Calling it from an anonymous block

DECLARE
  v_new employees.salary%TYPE;
BEGIN
  give_raise(p_emp_id => 105, p_percent => 10, p_new_salary => v_new);
  DBMS_OUTPUT.PUT_LINE('New salary: ' || v_new);
  ROLLBACK;                                      -- just testing: undo it
END;
/
New salary: 85800
ModeMeansIn OIC’s mapper
INValue goes into the procedure (the default)A field in the request you map into
OUTValue comes back outA field in the response you map from
IN OUTGoes in, may come back changedBoth

Notice what’s not in the procedure: a COMMIT. Small building-block procedures usually leave the commit to the caller, so they can be combined into bigger all-or-nothing work. The “main” procedure that OIC calls commits once at the end (chapter 10). p_emp_id => 105 is named notation: clearer than relying on position. If a procedure doesn’t compile, run SELECT * FROM user_errors; to see why.

8Functions

A function is a procedure that returns one value, so you can use it anywhere a value fits, even inside a SELECT, just like UPPER().

CREATE OR REPLACE FUNCTION get_dept_name (
  p_dept_id IN departments.dept_id%TYPE
) RETURN VARCHAR2 AS
  v_name departments.dept_name%TYPE;
BEGIN
  SELECT dept_name INTO v_name FROM departments WHERE dept_id = p_dept_id;
  RETURN v_name;
EXCEPTION
  WHEN NO_DATA_FOUND THEN
    RETURN 'Unknown';
END get_dept_name;
/

SELECT first_name, get_dept_name(dept_id) AS dept
FROM   employees WHERE emp_id IN (104, 109) ORDER BY emp_id;
FIRST_NAME DEPT
---------- -------
Sneha      IT
Vikram     Unknown
ProcedureFunction
ReturnsZero or more values through OUT parametersExactly one value with RETURN
Used in a SELECT?NoYes
Typical jobDo work: load, update, processCalculate or look up a value

A function that reads a table for every row can be slow on millions of rows: here a plain LEFT JOIN would be faster. Use functions for reusable logic, not as a replacement for joins.

9Packages: spec and body

The restaurant menu and the kitchenThe menu tells customers what they can order. The kitchen behind the door holds the recipes, and some kitchen-only prep work customers never see. A package has a spec (the menu: what others can call) and a body (the kitchen: the code, including private helpers).

The spec

CREATE OR REPLACE PACKAGE hr_int AS
  PROCEDURE load_staged_employees (
    p_run_name IN  VARCHAR2,
    p_merged   OUT NUMBER,
    p_errors   OUT NUMBER);

  FUNCTION get_dept_name (p_dept_id IN NUMBER) RETURN VARCHAR2;
END hr_int;
/

Call package members with a dot: hr_int.get_dept_name(30). Real projects keep integration code in packages like this (often named xx_…_pkg or …_int_pkg). OIC’s Invoke a Stored Procedure lets you pick the schema, then the package, then the procedure inside it.

10A real integration procedure

The goods-receiving bayA warehouse doesn’t put deliveries straight onto shelves. They go to a receiving bay first, get checked, the good ones are shelved, damaged ones are set aside with a note, and the clerk signs the register. That’s the staging pattern, and it’s the most common way OIC and databases work together.

The package body (full version in the practice file)

CREATE OR REPLACE PACKAGE BODY hr_int AS

  -- private: not in the spec, so only this package can call it
  PROCEDURE log_run (p_run_name IN VARCHAR2, p_status IN VARCHAR2, p_message IN VARCHAR2) IS
  BEGIN
    INSERT INTO integration_log (run_name, status, message)
    VALUES (p_run_name, p_status, SUBSTR(p_message, 1, 400));
  END log_run;

  PROCEDURE load_staged_employees (p_run_name IN  VARCHAR2,
                                   p_merged   OUT NUMBER,
                                   p_errors   OUT NUMBER) IS
  BEGIN
    -- ① validate: the department must exist
    UPDATE employee_stg s
    SET    s.process_status = 'ERROR',
           s.error_message  = 'Unknown department ' || s.dept_id
    WHERE  s.process_status = 'NEW'
    AND    NOT EXISTS (SELECT 1 FROM departments d WHERE d.dept_id = s.dept_id);
    p_errors := SQL%ROWCOUNT;

    -- ② upsert the good rows (the MERGE from Part 4.2)
    MERGE INTO employees e
    USING (SELECT * FROM employee_stg WHERE process_status = 'NEW') s
    ON    (e.emp_id = s.emp_id)
    WHEN MATCHED THEN UPDATE SET …
    WHEN NOT MATCHED THEN INSERT …;
    p_merged := SQL%ROWCOUNT;

    -- ③ mark them done
    UPDATE employee_stg SET process_status = 'PROCESSED' WHERE process_status = 'NEW';

    -- ④ + ⑤ log and save, all together
    log_run(p_run_name, 'SUCCESS', p_merged || ' merged, ' || p_errors || ' rejected');
    COMMIT;

  EXCEPTION
    WHEN OTHERS THEN
      ROLLBACK;                                 -- undo ①–③
      log_run(p_run_name, 'FAILED', SQLERRM);   -- remember why
      COMMIT;                                   -- keep the log row
      RAISE;                                    -- and tell OIC it failed!
  END load_staged_employees;

  FUNCTION get_dept_name (p_dept_id IN NUMBER) RETURN VARCHAR2 IS … END;

END hr_int;
/

Run it with one bad row in staging (dept 99)

DECLARE
  v_merged NUMBER; v_errors NUMBER;
BEGIN
  hr_int.load_staged_employees('manual-test-1', v_merged, v_errors);
  DBMS_OUTPUT.PUT_LINE('Merged: ' || v_merged || ', errors: ' || v_errors);
END;
/
Merged: 3, errors: 1
SELECT emp_id, process_status, error_message FROM employee_stg ORDER BY emp_id;
EMP_ID PROCESS_STATUS ERROR_MESSAGE
------ -------------- ---------------------
   104 PROCESSED
   108 PROCESSED
   111 PROCESSED
   113 ERROR          Unknown department 99

Read the EXCEPTION section slowly, because it’s the whole lesson: if anything fails, undo the data changes, record the failure, commit only the log, then re-raise so OIC’s fault handler knows. And run it a second time: Merged: 0, errors: 0, because nothing is NEW any more. Safe to re-run, just like MERGE.

11Set-based thinking

One trip or a thousandTo move 1,000 bricks you don’t carry them one at a time; you use a wheelbarrow. A loop that runs one UPDATE per row makes the database do 1,000 small trips. One UPDATE or MERGE with a WHERE does the same work in one trip. Oracle people call row-by-row processing “slow-by-slow”.

Slow-by-slow

FOR r IN (SELECT emp_id FROM employees
          WHERE dept_id = 10) LOOP
  UPDATE employees
  SET    salary = salary * 1.10
  WHERE  emp_id = r.emp_id;
END LOOP;

Set-based

UPDATE employees
SET    salary = salary * 1.10
WHERE  dept_id = 10;
-- same result, one statement

Our staging procedure is set-based: one UPDATE, one MERGE, one UPDATE, whether there are 3 rows or 300,000. The same rule applies one level up: don’t make OIC loop over 10,000 records calling the database once per record if one procedure call can process the whole batch. When row-by-row logic really is needed, PL/SQL has BULK COLLECT and FORALL to fetch and change rows in large batches.

12JSON inside the database

Integrations often store raw payloads in a CLOB column (“what exactly did we receive?”), or pass JSON into a procedure. Oracle can read and build JSON directly in SQL, using the same paths you learned in Phase 2.

JSON_VALUE: pick one value

SELECT JSON_VALUE('{"emp":{"id":101,"name":"Ravi"}}', '$.emp.name') AS name FROM dual;
NAME
----
Ravi

JSON_TABLE: turn a JSON array into rows

SELECT jt.id, jt.name
FROM   JSON_TABLE(
         '{"employees":[{"id":201,"name":"Kiran"},{"id":202,"name":"Asha"}]}',
         '$.employees[*]'                                 -- one row per array item
         COLUMNS (id   NUMBER       PATH '$.id',
                  name VARCHAR2(30) PATH '$.name')) jt;
ID  NAME
--- -----
201 Kiran
202 Asha

JSON_OBJECT: build JSON from a row

SELECT JSON_OBJECT('id' VALUE emp_id, 'name' VALUE first_name) AS payload
FROM   employees WHERE emp_id = 104;
PAYLOAD
-------------------------
{"id":104,"name":"Sneha"}

$ is the root, . goes into an object, [*] means every array item: the same idea as XPath in Phase 2, in JSON form. With JSON_TABLE, a procedure can accept one JSON CLOB from OIC holding hundreds of records and load them all with a single INSERT … SELECT: set-based again.

13How OIC connects to a database

The courier and the gated societyA courier can deliver straight to a shop on the main road. But a flat inside a gated society needs someone inside to come to the gate and collect it. Cloud databases are the shop; a database inside a company’s own network needs the connectivity agent, a small program installed inside that network that collects OIC’s requests.
AdapterConnects to · with
Oracle Autonomous Transaction Processing (ATP) / Autonomous Data Warehouse (ADW)Oracle’s cloud databases · the database wallet (a zip file of connection certificates), a service name, and a database user
Oracle DatabaseAny Oracle database, typically on-premises · host, port, service name, user · usually through the connectivity agent
MySQL, Microsoft SQL Server, PostgreSQL, IBM DB2 and othersThe same ideas for other databases

Security from Part 3.3 applies here too: OIC should connect as a dedicated integration user that has only the grants it needs (for example EXECUTE on one package and SELECT on one view), never as the schema owner or an admin. And the connection’s Test button checks the wallet, network path and password before you build anything.

14What the database adapter can do

Operation (invoke)What you give itUse it for
Run a SQL StatementA SQL statement with parameters written as #name; OIC validates it and builds the request and response shapesSimple queries and one-off DML
Invoke a Stored ProcedurePick schema → package → procedure. IN parameters become request fields, OUT parameters become response fieldsAnything multi-step or all-or-nothing
Perform an Operation On a TablePick tables and an operation (insert, update, merge, select); OIC generates the SQLPlain table writes, no SQL to type

Run a SQL Statement with parameters

SELECT emp_id, first_name, last_name, job_title
FROM   emp_details_v
WHERE  dept_name = #deptName
AND    last_update_date > TO_TIMESTAMP(#lastRunTime, 'YYYY-MM-DD"T"HH24:MI:SS')
-- OIC shows deptName and lastRunTime as request fields to map,
-- and the four columns as repeating response elements

Polling: the database as a trigger

As a trigger, the adapter can poll a table for new rows. With the logical delete strategy you choose a status column (the Logical Delete Field), the value meaning “not yet read” (Unread Value, e.g. NEW), the value it writes after reading (Read Value, e.g. PROCESSED), and how often to check (Polling Frequency). That’s exactly our process_status column. Rows too big for one message can be marked with a Rejected Value: messages are limited to 10 MB, so batch big data rather than pulling whole tables.

Database errors (constraint violations, your own ORA-20001) come back as faults with the ORA code and message, which you handle in Phase 7.

15Bind variables and SQL injection

The fill-in-the-blank formA bank form says “Pay ____ rupees to ____”. Whatever you write in the blanks is treated as an amount and a name, never as a new instruction. If instead the clerk copied your whole note into the instruction book, a note saying “…and also empty the vault” would be obeyed. Bind variables are the blanks on the form.

Dangerous: gluing input into SQL text

v_sql := 'SELECT * FROM employees
          WHERE last_name = ''' || p_input || '''';
-- p_input = x' OR '1'='1
-- becomes: WHERE last_name = 'x' OR '1'='1'
-- → every employee is returned

Safe: a bind variable

EXECUTE IMMEDIATE
  'SELECT COUNT(*) FROM employees
    WHERE last_name = :name'
  INTO v_count
  USING p_input;
-- the input is only ever a VALUE

That attack is called SQL injection, and it’s one of the oldest security holes on the web. OIC’s #parameters are bind variables, so values you map in are always treated as data. Binds are also faster: Oracle reuses the same execution plan instead of re-planning a “new” statement for every different value. Rule: never build SQL by joining strings with values from outside.

18Self-check

Answer in your head first, then tap to check.

1. Name the four sections of a PL/SQL block. Which are required?

DECLARE (optional), BEGIN (required), EXCEPTION (optional), END (required).

2. What does %TYPE give you?

A variable with the same data type as a column, so the code adapts if the column changes.

3. Which two errors can SELECT … INTO raise?

NO_DATA_FOUND (no row) and TOO_MANY_ROWS (more than one row).

4. Procedure vs function?

A procedure does work and returns values through OUT parameters; a function returns exactly one value and can be used inside SQL.

5. What range must your own error numbers use, and how do you raise one?

−20000 to −20999, with RAISE_APPLICATION_ERROR(-20001, 'message').

6. Package spec vs body?

The spec lists what others can call; the body holds the code, including private helpers not in the spec.

7. In the loader’s EXCEPTION section, why ROLLBACK, log, COMMIT, then RAISE?

Undo the half-done data changes, record why it failed, keep only the log row, and re-raise so OIC sees the failure.

8. When does OIC need the connectivity agent for a database?

When the database is inside a private (on-premises) network that OIC can’t reach directly.

9. Name the three invoke operations of the database adapters.

Run a SQL Statement, Invoke a Stored Procedure, and Perform an Operation On a Table.

10. In logical delete polling, what are the Read and Unread values?

Unread marks rows still to process (e.g. NEW); Read is written after the adapter picks them up (e.g. PROCESSED), so they aren’t read again.

11. Why are bind variables safer than building SQL with ||?

Input is treated only as a value, never as SQL, which prevents SQL injection; binds also let Oracle reuse the execution plan.

All of it, in one sentence

PL/SQL wraps SQL in blocks with variables, IF, loops and exceptions; saved as procedures, functions and packages, it lets OIC call one all-or-nothing, set-based, logged unit of work, through the ATP or Database adapter (via the connectivity agent on-premises) using Run a SQL Statement, Invoke a Stored Procedure, table operations or polling, always with bind parameters.
