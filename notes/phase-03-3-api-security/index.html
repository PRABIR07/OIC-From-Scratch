1Three questions every API asks

Sending money at a bankThe cashier asks: Who are you? (show ID). Are you allowed? (is this your account, within your limit?). And the money travels in a sealed bag so nobody opens or swaps it on the way. API security answers the same three questions.

Who are you?

Authentication. Password, API key or token. Fails with 401.

Are you allowed?

Authorization. Roles, scopes, permissions. Fails with 403.

Was it seen or changed?

Confidentiality & integrity. HTTPS (Phase 1) and signatures (chapter 13).

Everything else in this part is a different way of answering the first two questions. HTTPS always answers the third, which is why none of these methods are safe over plain HTTP.

2Where credentials travel

Almost always in one header, Authorization, whose value starts with a scheme word that says what kind of proof follows:

HeaderMeans
Authorization: Basic dXNlcjpwYXNzd2Q=Username and password, Base64-encoded (ch. 3)
Authorization: Bearer eyJhbGci…“Whoever bears this token may enter” (OAuth, JWT)
x-api-key: 9f2c…An API key, in a custom header (ch. 4)
<wsse:Security> in the SOAP HeaderWS-Security (Part 3.2)

Bearer literally means “the one carrying it”, like a cinema ticket: the usher doesn’t check your name, only the ticket. So a bearer token is as good as a password while it’s valid. Anyone who steals it can use it.

3Basic Auth, step by step

The security guardYou walk up to the gate. The guard says “ID please.” You show it, and you’re in. Next time, you show it again, because the guard doesn’t remember faces. Basic Auth sends the username and password with every single call.

Why it’s still used

Simple, universal, every tool supports it. Many Oracle Fusion integrations use it with a dedicated integration user.

Its weak spots

The real password travels on every call; if it leaks, it works until someone changes it; and password expiry can silently break integrations overnight.

Real-world tip: integration users should have a password that doesn’t expire unexpectedly, or a calendar reminder to rotate it. “The integration stopped at midnight with 401s” is very often an expired password.

4API keys

The gym cardThe gym gives your membership card a code. At the door they scan the card, not your face. If you lose it, they cancel that card and print a new one; your account is fine. An API key identifies an application, not a person, and can be replaced without touching anyone’s password.
Sent asExampleVerdict
Custom headerx-api-key: 9f2c71…Preferred
Authorization headerAuthorization: ApiKey 9f2c71…Fine
Query parameter?api_key=9f2c71…Avoid: it lands in logs

Good practice: one key per application and per environment (test key ≠ production key), and rotate keys on a schedule: create the new key, switch the connection, then delete the old one. API keys usually can’t express fine-grained permissions, which is where OAuth comes in.

5Why OAuth exists

The valet keySome cars come with a valet key: it starts the car and opens the door, but not the boot or the glovebox, and you can take it back any time. You’d never give the valet your house keys too. OAuth 2.0 gives an app a limited, temporary key instead of your real password.
Problem with passwordsHow OAuth solves it
The password travels on every callIt’s exchanged once; then only a short-lived access token travels
A leaked password works foreverTokens expire, often within an hour
A password can do everythingTokens carry scopes: only what was granted
Revoking means changing the password everywhereRevoke one app’s access; nothing else changes
Each API stores and checks passwordsOne authorization server handles all logins

6OAuth’s four roles

The hotelThe guest owns the stay. The travel agent books on the guest’s behalf. The reception checks identity and hands out key cards. The room door only checks the card. OAuth names these four roles.

A grant type (or “flow”) is the exact sequence of steps the client follows to get a token. Which grant you use depends on whether a person is involved.

7Client credentials: the exact HTTP

A company’s delivery vanThe van driver doesn’t log in as any particular employee. The company itself is registered with the warehouse, and the warehouse issues a day pass to the van. Client credentials is OAuth for system-to-system calls: the app proves its own identity, with no person involved. It’s the flow you’ll use most in OIC.

8Authorization code: when a person must say “Allow”

“Sign in with Google”A photo-printing website wants your Google Photos. It sends you to Google. You log in at Google (the website never sees your password), click Allow, and Google sends you back with a one-time code. Behind the scenes, the website swaps that code for a token. That’s the authorization code flow.

Why the extra code step instead of handing the token straight to the browser? Because the browser is a public place. The code is useless on its own: only the app, using its client secret in a private server-to-server call, can turn it into a token. Apps without a safe place for a secret (mobile apps, single-page web apps) add PKCE, a one-time random proof that the same app that started the flow is finishing it.

9Refresh tokens

The day pass and the membershipA theme park gives you a day pass (access token) and keeps your annual membership on file (refresh token). Tomorrow you show the membership at the counter and get a new day pass, without filling the forms again. A refresh token gets new access tokens without asking the person to log in again.
Access tokenRefresh token
Sent toThe API, on every callOnly the auth server
LifetimeShort: minutes to an hourLong: days to months
If stolenUseful until it expiresVery dangerous: guard it carefully
Client credentials?YesUsually not needed: just ask again with the secret

11Scopes and least privilege

The office key ringA new intern doesn’t get the master key. They get the keys to the 3rd floor and the pantry. A scope is a named permission requested with the token. Ask for the smallest set that does the job.

Scopes answer “what may this app do”. Roles answer “what may this user do”. In Oracle Fusion, a 403 usually means the integration user is missing a role; with OAuth APIs, it can also mean the token is missing a scope.

12JWT: every claim explained

The boarding passYour boarding pass shows who issued it (the airline), who you are, which flight, boarding time and when it’s no longer valid, plus a barcode the airline signed. A JWT carries the same kinds of facts, called claims, plus a signature.
ClaimFull nameMeansBoarding pass
ississuerWhich auth server created itThe airline
subsubjectWho or what it’s about (user or client ID)Passenger name
audaudienceWhich API it’s meant for. Other APIs must reject it.Flight number
expexpiryNot valid after this time (epoch seconds)Gate closes

Base64URL is Base64 made safe for URLs: + and / become - and _, and the = padding is dropped. That’s why JWTs never contain those characters.

13How signatures work

Two kinds of sealHS256 is like a family secret recipe: whoever knows the secret can both make the dish and check it’s authentic. RS256 is like a government seal: only the government owns the stamp (private key), but everyone has a picture of the seal (public key) to check stamps against. Change one letter of the token, and the seal no longer matches.
algSigned withVerified with
HS256A shared secretThe same shared secret
RS256A private key, kept by the issuerThe matching public key (anyone)
Signed is not encrypted. A signature proves nobody changed the token; it doesn’t hide anything. That’s why secrets never go in a JWT, and why tokens still need HTTPS. In chapter 16 you’ll change a claim yourself and watch the check fail.

Opaque tokens are the other kind: a random string with no meaning inside. The API must ask the auth server “is this valid?” every time. JWTs let the API check by itself, which is faster.

14Oracle’s auth server: OCI IAM

In Oracle Cloud, the “reception desk” is OCI IAM (Identity and Access Management), organised into identity domains. Its token URL looks like https://idcs-<id>.identity.oraclecloud.com/oauth2/v1/token. OIC itself, and many Oracle SaaS apps, trust tokens from it.

So the flow you learned in chapter 7 works both ways: OIC uses it to call other APIs, and other systems use it to call your OIC integrations. You register the caller as a confidential application in the identity domain, give it the right scope for your OIC instance, and hand its client ID and secret to whoever builds the caller. Your OIC administrator usually sets this up.

15Token and secret hygiene

Never log them

Logs are read by many people. Mask tokens, passwords and keys.

Never hard-code

Keep them in the OIC connection or a vault, never in a mapping or code.

Separate environments

Different credentials for test and production.

Rotate

Change secrets on a schedule, and immediately after anyone leaves.

Least privilege

Smallest roles and scopes that do the job.

Check the clock

Token checks use time. A server with a wrong clock rejects valid tokens.

1 · Watch the Basic Auth challenge

HTTP/2 401

{ "authenticated": true, "user": "user" }
echo -n 'user:passwd' | base64   →   dXNlcjpwYXNzd2Q=

2 · See exactly what a token request looks like

# httpbin.org/anything echoes back whatever it receives, so we can SEE the request.
# It doesn't issue real tokens; a real auth server would answer with access_token.
curl -s -X POST https://httpbin.org/anything \
  -u my-client-id:my-client-secret \
  -d grant_type=client_credentials -d scope=hr.read
"form": { "grant_type": "client_credentials", "scope": "hr.read" },
"headers": { "Authorization": "Basic bXktY2xpZW50LWlkOm15LWNsaWVudC1zZWNyZXQ=",
             "Content-Type": "application/x-www-form-urlencoded", … }
curl -d sends a form body, and -u builds the Basic header from the client ID and secret.

17Where this shows up in OIC

OIC security policy (connection)What OIC does for you
Basic AuthenticationAdds Authorization: Basic … from the username and password you enter
API Key Based AuthenticationSends your key in the header or query parameter you specify
OAuth Client CredentialsCalls the token URL with the client ID, secret and scope, caches the token, and refreshes it when it expires
OAuth Authorization Code CredentialsRuns the browser login once (you click “Provide Consent”), then keeps tokens refreshed
OAuth Custom Two/Three Legged FlowFor servers that don’t follow the standard exactly: you describe each request yourself
Username Password Token (SOAP)Adds the WS-Security UsernameToken to the SOAP Header (Part 3.2)
No Security PolicyNothing added: for public APIs only

The other direction: when another system calls your integration’s REST trigger, OIC checks its credentials, typically an OAuth token from your OCI IAM identity domain (chapter 14).

Test the connection. OIC connections have a Test button. For OAuth it actually fetches a token, so a failure there points straight at the client ID, secret, token URL or scope, before you build anything.

  1. 1
    JSON body for the token requestThe token URL wants application/x-www-form-urlencoded.
  2. 2
    Client secret in the wrong placeBasic header vs form body: the docs decide. Wrong choice → invalid_client.
  3. 3
    Wrong scope or audienceThe token is valid, but for another API → 401 or 403.
  4. 4

  5. 5

  6. 6
    Sharing tokens in screenshots or chatsA bearer token works for whoever holds it.
  7. 7
    401 vs 403 confusion401: fix the credentials. 403: fix the roles or scopes.

19Self-check

Answer in your head first, then tap to check.

1. What does a 401 response’s WWW-Authenticate header tell you?

Which kind of credentials the server wants (for example Basic or Bearer).

2. Why is an API key safer in a header than in the query string?

URLs, including query strings, get written into logs and histories.

3. Name OAuth’s four roles.

Resource owner, client, authorization server, resource server.

4. In client credentials, what’s the token request’s Content-Type and grant_type?

application/x-www-form-urlencoded and grant_type=client_credentials.

5. What three fields come back in a token response?

access_token, token_type (Bearer) and expires_in (plus sometimes scope and refresh_token).

6. Why does the authorization code flow use a code instead of returning the token to the browser?

The browser is public; only the app, with its secret in a server-to-server call, can turn the code into a token.

7. What do aud and exp mean in a JWT?

aud: which API the token is for. exp: when it stops being valid.

8. HS256 vs RS256?

HS256: one shared secret signs and verifies. RS256: a private key signs; a public key verifies.

9. You change one letter of a JWT’s payload. What happens?

The signature no longer matches, so verification fails.

10. Which OIC security policy fits system-to-system OAuth?

OAuth Client Credentials.

All of it, in one sentence

APIs ask who are you (401) and are you allowed (403); Basic Auth and API keys send a fixed secret every time, while OAuth swaps it once at the token URL for a short-lived Bearer token with scopes, often a signed JWT whose claims anyone can read but nobody can change; and OIC’s security policies do all of this for you.
