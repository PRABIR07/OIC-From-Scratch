REST in depth

Phase 3 is in four parts: 3.1 REST · 3.2 SOAP & WSDL · 3.3 API security · 3.4 Real-world APIs. In this part we read a REST call line by line, and learn every rule that decides whether it works.

1What an API really is

The menu and the waiterIn a restaurant you never enter the kitchen. You read the menu (what you may order, and how to ask), and the waiter carries orders in and food out. An API (Application Programming Interface) is a system’s menu and waiter. The kitchen (database, code, rules) stays hidden, and can be rebuilt without changing the menu.

An API is a contract: “send me exactly this, and I promise to answer with exactly that.” Every rule in this part exists so both sides can keep that promise without ever talking to each other.

2One REST call, line by line

X-ray visionTools like Postman and OIC hide the raw message behind nice screens. But on the wire, every request and response is just lines of text in a fixed order. Once you can read these lines, no API error can confuse you.
LineWhat it tells the other side
POST /api/v1/employees HTTP/1.1Do a POST (create) on the resource /api/v1/employees, speaking HTTP version 1.1
Host:Which website on that server (one server can host many)
Content-Type:The body I’m sending is JSON
Accept:Please answer in JSON
Authorization:My proof of identity (part 3.3)
201 CreatedIt worked, and something new exists now
Location:Here is the address of the new thing: employee 102
X-Request-Id:A tracking number for this call. Quote it when you raise a support ticket.

HTTP/2 (which you saw in Phase 1’s curl output) sends the same information in a faster binary form, so tools still show it to you as these lines.

3Designing good addresses

A well-run libraryShelves are labelled with what they hold (“Fiction”, “History”), never with what you do there (“Borrow-books-shelf”). Inside a shelf, each book has a number; inside a book, chapters. REST addresses are labelled with nouns; the HTTP method supplies the verb.
AvoidPreferRule
GET /getEmployee?id=101GET /employees/101Nouns, not verbs
POST /createEmployeePOST /employeesMethod is the verb
/Employee, /employee/employeesPlural, lowercase
/pay_slips, /paySlips/pay-slips or /payslipsHyphens, consistent
/employees/101/deleteDELETE /employees/101No actions in the path

Real APIs bend these rules sometimes. When an action truly isn’t create/read/update/delete, many APIs use a POST to an action address, like POST /orders/501/cancel. Oracle Fusion has these too. Recognise the pattern; don’t be surprised by it.

4Methods and the answers they expect

Phase 1 introduced the methods. In practice you also need to know what a good API answers for each one, because OIC checks those answers.

MethodOnSuccess answerBody?Repeat-safe
GET/employees or /employees/101200 + the dataNoYes
POST/employees201 + Location header + new itemYesNo
PUT/employees/101200 + item, or 204Yes, completeYes
PATCH/employees/101200 + item, or 204Yes, partialNot always
DELETE/employees/101204 (or 200)Usually noYes
HEADanySame headers as GET, no bodyNoYes
OPTIONSanyWhich methods are allowed (Allow header)NoYes
Two extra methods worth knowing. HEAD is “just show me the label, not the parcel”: useful to check a file’s size or whether something exists, without downloading it. OPTIONS asks “what am I allowed to do here?”, and browsers send it automatically before some cross-site calls.

5Four places to put data

A courier bookingThe address says which house (path). Stickers on the box say “fragile, deliver after 6 pm” (query and headers). The parcel holds the goods (body). Every value in a REST call lives in one of four places, and each place has a job.
PlaceUse it forExampleOIC name
PathIdentifying one resource/employees/101Template parameter
QueryFilters, sorting, paging, options?dept=HR&limit=50Query parameter
HeaderInformation about the call: auth, format, trackingAccept-Language: hiStandard / custom header
BodyThe data you create or change{"city":"Mumbai"}Request payload

Never put secrets in the path or query. Full URLs get saved in server logs, browser history and proxies. Passwords and tokens belong in headers.

6Headers that matter

Request headerMeans
Content-TypeFormat of the body I send
AcceptFormat I want back
AuthorizationWho I am (3.3)
User-AgentWhich program is calling
If-None-Match“Only send it if changed” (ch. 10)
Idempotency-Key“If you’ve seen this key, don’t create twice” (3.4)
Response headerMeans
Content-TypeFormat of the body I return
LocationAddress of the new item, or redirect
ETagA fingerprint of this version (ch. 10)
Cache-ControlHow long you may reuse this
Retry-AfterSeconds to wait before retrying
X-Request-IdTracking number for support

Header names are not case-sensitive: content-type and Content-Type are the same (HTTP/2 always shows them lowercase). Headers starting with X- are custom ones invented by that API.

7Content-Type vs Accept

Speaking with a translatorYou tell the translator two things: “I am speaking Hindi” and “please answer me in English”. Content-Type is “the language I’m sending”; Accept is “the language I want back”. They’re different questions, and mixing them up is a classic bug.
Media typeMeans
application/jsonJSON
application/xml or text/xmlXML (SOAP 1.1 uses text/xml)
application/x-www-form-urlencodedkey=value&key2=value2, like a web form. OAuth token requests use it (3.3)
multipart/form-dataSeveral parts in one body, e.g. a form with a file upload
application/octet-streamRaw bytes: a file
application/vnd.oracle.adf.resourceitem+jsonA vendor-specific JSON flavour. Oracle Fusion uses names like this.

8Errors done right

A good doctorA bad doctor says “you’re sick”. A good doctor says what is wrong, where, and what to do. A good API returns the right status code AND a body that explains the problem.
SituationCodeWho fixes it
Created something201Nobody: success
Accepted, will finish later202Check back later (3.4)
Broken JSON, wrong type, missing field400You: fix the request
Valid JSON but breaks a business rule (end date before start date)422You: fix the data
No or bad credentials / not allowed401 / 403You: credentials or roles
No such resource404You: URL or ID
Already exists / clashes409You: check before creating
Wrong body format415You: Content-Type
Too many calls429Wait, then retry
Their bug / down / slow500 / 503 / 504Them; retry later
Always read the error body, not just the code. In OIC, the fault details in monitoring include the response body the other system sent. The answer to “why did it fail?” is usually written right there.

9Stateless, and why it matters

The call centreWhen you call a bank, you might reach a different agent every time. So you repeat your account number on every call. If agents relied on remembering you, the bank couldn’t simply add more agents on a busy day. Stateless means every request carries everything needed, so ANY server can answer it.

So in REST, the token goes on every call, and “page 3” is asked for explicitly (?offset=200), never “give me the next one”. The server doesn’t keep your place.

10Caching & ETags

The newspaper boyYou ask: “Is there a new edition? I have edition 412.” If nothing changed, he says “no change” and gives you nothing to carry. An ETag is the edition number of a resource; If-None-Match asks “only send it if it’s not edition 412”.

The same fingerprint also protects updates. Send If-Match: "v412" with a PATCH, and if someone else changed the record meanwhile, the server answers 412 Precondition Failed instead of silently overwriting their change. Oracle Fusion REST supports this kind of check too.

Cache-Control: max-age=60 says “you may reuse this answer for 60 seconds without asking again”. no-store says “never save this”, which is common for personal or financial data.

11Versioning

Changing a bus routeIf a city suddenly changes bus route 12, everyone who relied on it ends up in the wrong place. Smart cities launch route 12A and keep route 12 running for a while. APIs keep the old version alive and publish the new one beside it.
Breaking changeSafe change
Renaming a fieldAdding a new optional field
Removing a fieldAdding a new endpoint
Changing a field’s typeAdding a new optional query parameter
Making an optional field requiredAccepting more values than before
Where the version goesExample
In the path/api/v2/employees
In a headerApi-Version: 2
Oracle Fusion/hcmRestApi/resources/11.13.18.05/workers

A breaking change is anything that would make an existing caller fail. That’s why OIC integrations pin the version in the Relative Resource URI: an upgrade on the other side can’t break you without notice.

12OpenAPI: the menu card in a standard format

A printed menu vs a chalkboardSome restaurants scribble today’s dishes on a chalkboard; others print a proper menu with prices, sizes and allergens. OpenAPI (once called Swagger) is a standard printed menu for REST APIs, written in YAML or JSON, that people and tools can both read.

Every idea from Phases 1–2 has a slot: servers = base URL, paths = endpoints, in: path / query / header = the four places, responses = status codes, schemas = the rule book. Websites like editor.swagger.io turn this into a clickable page where you can try each call.

13Polling vs webhooks

The birthday cakeYou can phone the bakery every 10 minutes: “Is my cake ready?” (polling). Or you leave your number and they call you when it’s ready (webhook). A webhook is an API call made BY the other system TO you, when something happens.

In OIC, a scheduled integration that checks for new records is polling. An integration with a REST trigger that another system calls when something happens is receiving a webhook. Oracle Fusion’s business events (Phase 8) are the same idea.

14Try it yourself

1 · See the raw request and response lines

curl -v https://jsonplaceholder.typicode.com/posts/1 -o /dev/null
> lines = your request (request line, Host, User-Agent, Accept)
< lines = the response (status line, then headers)
-o /dev/null hides the body so you can focus on the lines

2 · HEAD: the label without the parcel

curl -I https://jsonplaceholder.typicode.com/posts/1
only the status line and headers come back: no body

3 · POST and see 201

curl -i -X POST https://jsonplaceholder.typicode.com/posts \
  -H "Content-Type: application/json" \
  -d '{"title":"REST in depth","userId":1}'
HTTP/2 201  … then the new item with "id": 101

4 · See exactly which headers you sent

curl -s https://httpbin.org/headers -H "Accept: application/json" -H "X-Request-Id: my-test-1"
httpbin echoes back the headers it received, including your custom one

5 · ETag and 304 Not Modified

curl -sI https://api.github.com/users/octocat | grep -i etag
etag: W/"abc123…"    ← copy the whole value inside the quotes
curl -sI https://api.github.com/users/octocat -H 'If-None-Match: W/"abc123…"' | head -1
HTTP/2 304              ← nothing changed, no body sent

6 · Read a real OpenAPI menu

Open https://petstore3.swagger.io in a browser. Expand GET /pet/{petId},
click “Try it out”, enter 1, and Execute. It shows the curl command,
the request URL, the response code and body: every piece from this part.

16Common mistakes

  1. 1
    Accept vs Content-Type swappedYou get 415 or 406. Content-Type describes what you send; Accept what you want.
  2. 2
    Reading only the status codeThe error body usually says exactly what’s wrong.
  3. 3
    A trailing or missing slash/employees/ and /employees can be different to some servers. Copy the path exactly from the docs.
  4. 4
    Wrong version in the pathCalling /v1 when the docs you read describe /v2.
  5. 5
    Secrets in the query stringThey end up in logs. Use headers.
  6. 6
    Ignoring the Location headerAfter a 201, the new item’s ID is often only there.
  7. 7
    Sample JSON with empty valuesOIC builds the structure from your sample: use realistic values and 2+ array items.

17Self-check

Answer in your head first, then tap to check.

1. What separates the headers from the body in a raw HTTP message?

One empty line.

2. Rewrite POST /createEmployee the REST way.

POST /employees. The method is the verb; the path is a noun.

3. After a successful POST, which code and which header do you expect?

201 Created, with a Location header pointing to the new item.

4. Where do filters go? Where do tokens go?

Filters in the query string; tokens in a header, never in the URL.

5. You send JSON but the server answers 415. Why?

It can’t read your body’s format: usually a missing or wrong Content-Type.

6. 400 vs 422?

400: the request itself is malformed. 422: it’s well-formed but breaks a business rule.

7. Why does statelessness help big systems?

Any server can answer any request, so a load balancer can spread calls across many servers.

8. What does a 304 Not Modified mean?

The resource hasn’t changed since the ETag you sent, so nothing was re-sent.

9. Is adding a new optional field a breaking change?

No. Removing or renaming a field is.

10. Polling vs webhook, in one line each?

Polling: you keep asking. Webhook: they call you when it happens.

All of it, in one sentence

A REST call is plain text: a request line, headers, a blank line and a body; good APIs use noun addresses, put each value in the right one of four places, answer with the right status code and error body, stay stateless, use ETags and versions, and describe themselves in OpenAPI.
